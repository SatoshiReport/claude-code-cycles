# Running Claude Code like an engineering team: one board, guarded agents, and cycles

This is a write-up of how one person runs a real production system (a multi-exchange
trading engine in Rust, plus Python analytics and two native Apple apps) almost entirely
through Claude Code.

None of this is a product. It is a set of conventions, skills, hooks and mods that grew
one incident at a time. We are sharing the shape of it because it works, and because parts
of it are only recently possible with **mods**. The code is tied to our system, so this document describes the method rather
than shipping files you can drop in.

---

## The shape in one paragraph

A **coordinator** session plans and reviews; it rarely writes code. It takes work from a
**board** (one Markdown file per work item, in the repo), hands each item to a **delegate**
agent with a narrow role (builder, reviewer, scout, sweeper), reviews what comes back,
gates it and commits it. A **cycle** chains the whole loop (audit, spec, build, CI, deploy,
close) with each stage in its own fresh session. **Hooks** refuse the classes of mistake
agents keep making, at the moment they make them. **Mods** run the loop itself: they
clear the session and start the next cycle, keep session ownership alive, and put the right
memory in front of the agent at the right tool call. The human (the "operator") steers
from a phone and mostly answers questions.

---

## 1. The board: one file per work item

Everything open lives in `audit/board/<id>.md`. Finished, verified items move to
`audit/board-archive/` with `git mv`. An index (`audit/board.md`) is generated by a script
and a hook refuses hand edits to it.

A row file looks like this:

```markdown
---
id: X1374
state: BUILD
progress: ready
lane: monitor
group: native-apps
owner:
spec:
spec_files:
minted: 2026-09-04
archived:
archive_note:
---
**THE SCREEN SHOWS PAPER POSITIONS AFTER YOU SWITCH TO LIVE** (found 2026-09-04 by ...)
USER-VISIBLE: ... CLOSE = ...

## Status
minted 2026-09-04 ...; BUILT 2026-09-05 (commit 7207165ff) ...; VERIFIED on the box ...
```

What made this work, in the order we learned it:

- **One file per row, not one big table.** We started with a single 841-line board file.
  Three concurrent sessions editing it collided on every status update. One file per row
  makes each row its own commit target.
- **A small, fixed set of states.** `BUILD`, `RUN-EVIDENCE` (we need to produce evidence),
  `WATCH` (built, waiting to be confirmed in production), `OPERATOR-DECIDES` (a question for
  the human), `OPERATOR-RUNS` (something only the human can do), `HOLD`. The state is the
  census. A lint fails unknown values.
- **Rows name the wrong behaviour, not the annoyance.** A row titled "too many alerts" invites
  someone to hide alerts. The same defect titled "the consumer books a fill before the order's
  acknowledgement has arrived" invites the real fix. The title anchors the fix.
- **Ids come from a tool, never from eyeballing max + 1.** Two sessions computing "the next
  id" by eye collided three times in one day. The minting tool reserves atomically and also
  refuses when the new headline looks like a duplicate of an open row until you name the
  candidates you checked.
- **An `owner:` field is the fence between sessions.** A session stamps its name when it
  takes a row. A mod writes a heartbeat every minute; a claim with no heartbeat and no row
  update for three hours is dead and any session may take it over, recorded as a takeover.
- **Nothing archives until it is verified in place.** "Tests pass" is not done. Done is:
  deployed, and the production log shows the alarm for the wrong outcome reading zero while
  the code path ran. Gate-green rows stay open until a watch closes them.
- **Status updates land in the same commit as the event.** Dispatched, built, deployed,
  verified: each lands on the row when it happens, not in an end-of-day summary.

## 2. Roles: the coordinator thinks, delegates produce

Agent role files live in `.claude/agents/`:

| role | model tier | does | never |
|---|---|---|---|
| builder | top tier | writes production code and tests against a spec and a file list | builds, commits |
| reviewer | top tier | reads a builder's diff against the spec, returns findings | gives the verdict |
| scout | mid tier | read-only evidence: grep, logs, live API reads | draws the conclusion |
| sweeper | small tier | mechanical fan-out with no judgment | changes code |

Rules that turned out to matter:

- **The coordinator keeps the diagnosis.** Root cause, design and the final correctness call
  stay with the coordinator. A wrong diagnosis costs more than the analysis would have.
- **Delegates report leads, not verdicts.** Every delegate claim is re-checked before it is
  used.
- **Delegates never build or commit.** Parallel compiles ran the machine out of memory, and
  parallel commits raced the shared git index. The coordinator gates and commits each unit,
  using pathspec commits (`git commit -- <paths>`) because several sessions share one tree.
- **Maximize parallel work, serialize only on file collisions.** A wave puts blockers
  first, then lays out rows in layers where no two rows touch the same file.
- **If a delegate gets the same task wrong twice, the coordinator writes it.**

## 3. The cycle

One `/cycle run` is five phases, each stage in a child session of its own, while the cycle
session only coordinates:

1. **Audit, drain and the weekly checks.** `/audit` reviews the code unit by unit (see
   "How the audit works" below). `/drain` reads every WATCH and RUN-EVIDENCE row against
   production and closes, re-opens or advances it. Beside them: dependency upgrades,
   mutation testing, `/changes` (what each external API we depend on has published since we
   last looked), a weekly `/rules` review of the rule files themselves, and a weekly
   `/security` read of the live cloud account and servers for exposure (open ports, public
   addresses, keys, logging and alerting switched off). The security check is read-only:
   each finding becomes a board row, and the fix lands in the script that provisions the
   resource, never as a hand change.
2. **Spec.** `/spec` researches open BUILD rows and stamps each with a premise, the files it
   touches, size and difficulty, the verification read, and the alarm it must ship with.
3. **Wave.** `/wave` composes a frontier of spec'd rows, dispatches delegates in parallel,
   gates and commits each return.
4. **CI.** One full CI run on the committed head.
5. **Ship.** On green CI, deploy to the two development boxes, watch the logs, take the
   deploy-dependent reads, and fix and re-ship within the cycle.

Then the close: a summary of what landed, what was archived, what was minted, and what
is waiting on the human. A mod sees that summary, types `/clear`, and starts the next cycle,
until the board holds no buildable row.

Children report to the parent over cross-session messages. A child is a normal Claude Code
session, so it shows in the Claude app and the human can open any one of them from the phone.

### How the audit works

- **Six lenses, recorded separately.** Each code unit is read by one finder agent per lens:
  rule violations (every hidden default swept), duplicate code, dead code and best practice,
  domain correctness, tests and latency, and security. Each lens keeps its own record of
  what it has read and at which commit.
- **What gets read next.** Never-reviewed code first, then code that changed since its last
  review, then a catch-up for any lens that has never read a unit, then a **rule sweep**:
  when a rule is added or widened, every unit a lens read before that date is read again
  for it. A lens that has read a unit before reports only on the code changed since.
- **Every finding names its impact.** Money, a silent failure, a wrong value on screen, a
  crash or stall, security, drift between two copies of one fact, a defect the code's
  shape invites (the wrong value, branch or edit named), or a written coding rule it
  breaks. Findings that are only taste, from a fixed list, are dropped.
- **Two rounds of disproof.** Skeptic agents try to refute each finding, then the
  coordinator re-reads the cited lines and drops anything that fails or whose impact does
  not hold. Each finding that survives becomes a board row citing `file:line`.
- **Reversals go to the human.** A finding that would undo an earlier design decision or a
  closed row is never built directly; it becomes a question for the human in the five-part
  form, naming the decision and what has changed since.
- **The audit improves its own rules.** A real defect that no rule names becomes a candidate
  rule: it is added to that lens, a rule sweep is scheduled over old code, and the build
  reviewer's checklist picks it up for new code.
- **Every finding is traced to the commit that wrote it.** The audit records whether the
  bad line passed through review or reached the tree by a path that skips review. A finding
  that review missed becomes a row to strengthen the reviewer's checklist or add a guard; a
  cluster of unreviewed commits becomes a row to route that path through review.

## 4. Hooks: refuse the mistake when it is made

We have about 30 guard hooks, each with its own tests. They fall into a few groups:

- **Irreversible or outward actions:** placing an exchange order, restarting a service,
  changing a log level, touching cloud credentials. These **block, then confirm**: the first
  attempt is refused; the agent may retry only by writing a line naming the board row or the
  human's order that authorizes it. Nothing opens a dialog, because the human is often on a
  phone.
- **Git hygiene:** one branch, no stash (hidden parallel state), no bulk `git add` in a shared
  tree, no attribution footers.
- **Code honesty:** the WHY test below; no em dashes; banned ambiguous words.
- **Secrets:** refuse commands that would print credential values; a mod (below) redacts any
  that slip into a tool result before the conversation stores it.
- **Process:** the board index is generated only; board timestamps come from `date -u`, not
  from the model's guess.

### The WHY test (the single most useful rule)

The most common failure of a coding agent is fixing an error by making it invisible: a
default value, a retry, a "safety net" re-scan, a lowered log level. Our rule: any code that
departs from the straight path must answer five questions in a comment:

1. What exact state or input makes this necessary?
2. Who produces it? (`file:line`, or a named external actor: an exchange, the OS, a library)
3. Would the normal path be correct without this? **If no, this is the design and the
   producer gets fixed instead.**
4. What is visible when it fires? (a log line or counter whose nonzero is a defect)
5. Does it make the wrong case impossible, or handle it after the fact?

Only two declarations are allowed:
`EXTERNAL -- source: <who produces it> -- why: ...` and
`DETECTOR -- counts: <what a nonzero means> -- why: ...`. A hook refuses the edit when
repair vocabulary (`heal`, `retry`, `best-effort`, `grace window`, `unwrap_or`, ...) appears
without one within three lines, and CI fails the same thing. Phrases like "self-heals" or
"the next pass re-reads it" count as unanswered.

A companion rule: **every fix ships with the alarm for its wrong outcome**, a WARNING-or-higher
log line with a test asserting it. The row then closes on "zero of that line while the code
ran", instead of waiting for the bug to happen again.

## 5. Mods: driving Claude Code itself

Hooks react to tool calls. **Mods** are TypeScript modules loaded into Claude Code that can
hook the session itself: read every turn, submit prompts, `/clear`, start sessions, and
print notices under an answer. This is what made the unattended loop possible. Ours:

| mod | what it does |
|---|---|
| `cycle-loop` | when a turn ends with a cycle's close summary, records it, types `/clear`, starts the next cycle; stops on an empty board or a failed board check, and prints a one-line reason under the answer either way |
| `owner-heartbeat` | notices when the session claims a board row and writes a heartbeat every minute, so other sessions can tell a live owner from a dead one at once instead of after three hours |
| `memory-at-hand` | a memory note can declare the tool call it governs (`<!-- when: Bash gdb.*attach -->`); the first matching call is held once and the note is shown to the agent at that moment, not only in an index it may never open |
| `prose-check` | checks the chat replies (which tool hooks cannot see) for banned words, em dashes and times without a time zone, and asks the model to restate the sentence |
| `secret-redact` | replaces credential-shaped values in tool results with `[REDACTED: <label>]` before they are stored, in the main session and in every subagent |
| `quota` | shows each account's usage, its burn rate and when that rate runs out, as a table under answers and short lines above the prompt |

The pattern behind all of them: **when a rule keeps being broken, it moves from prose
(CLAUDE.md) to a guard (hook or mod).** A rule nobody reads at the moment of the mistake
prevents nothing.

## 6. Steering from a phone

- **Questions go on the board, never only in chat.** Each one is an `OPERATOR-DECIDES` row
  with five parts: what raised it (with evidence), what it decides (money, screen, alarms
  first), the options, a worked example walking one real scenario through each option, and a
  recommendation. `/asks` lists them in plain words. The human should be able to decide from
  the presentation alone.
- **A board row is its own authorization.** If a row names the work, including a deploy or
  a bounded test trade, the cycle does it. Anything no row names needs a fresh yes.
- **Spending money never waits inside a cycle.** It waits on its own question row until the
  human answers, and the cycle works on everything else.

## 7. Rule files and memory

- A global `~/.claude/CLAUDE.md` (how to work: root causes, errors not defaults, verify
  before asserting, delegation, board discipline) and a workspace `CLAUDE.md` (this system's
  standing orders).
- Memory is one fact per file with a short index. Memory records traps and rulings the repo
  cannot show; it never repeats what git or CLAUDE.md already says.
- A weekly `/rules` review prunes stale, duplicated and contradictory rules. Without it the
  rule files grew past the point where a session could hold them in mind.

## 8. What it costs, and what went wrong

- **Usage.** Parallel delegates and child sessions burn through plan limits. The cycle checks
  usage before each wave and pauses when it would run out mid-wave.
- **Rule growth.** Every incident wants a new rule. Many of ours carry the date of the
  operator order that created them, which is great for us and noise for anyone else. The
  weekly review is the counterweight.
- **Guards that block good work.** A guard is a blunt string match. Each false refusal is
  fixed in the guard (with a test), not worked around.
- **Shared working tree.** Several sessions in one git tree need strict pathspec commits and
  a rule that delegates never commit. Worktrees helped for isolated experiments but start from
  a stale base if you are not careful.
- **Wrong diagnoses delegated to save tokens** cost more than they saved, every time.

## 9. Compared with Claude Code Projects

We do not use Projects, but people will ask. From Anthropic's announcement, the redesigned
Projects (beta, September 2026) gives a coordinator chat that splits a goal into parallel
cloud threads, each on its own branch, with shared project memory, PRs, per-role model and
effort settings, and per-project usage. That covers much of the session plumbing we built by
hand. What it does not describe: a visible work ledger with owners and verified-only
archiving, "done means confirmed in production" rather than "merged", hooks that refuse
classes of mistakes, a fixed cycle of stages, a structured format for questions to the human,
and reach into machines outside the cloud.

## 10. If you want to try the core of this

You do not need all of it. The parts we would keep first:

1. A board directory with one file per item, a generated index, an id-minting script, and an
   `owner:` field.
2. Three role files: builder, reviewer, scout. The coordinator never builds or commits in
   parallel.
3. The WHY test as a CLAUDE.md rule plus one edit hook that refuses repair vocabulary without
   a declaration.
4. "Block, then confirm" hooks for whatever is irreversible in your world.
5. Questions as board rows in the five-part form.
6. One mod that restarts the loop when a cycle closes.
